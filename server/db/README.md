# PostgreSQL persistence

`migrate(pool)` applies numbered SQL files transactionally and records their SHA-256 checksums in `schema_migrations`. Applied files are immutable; add a new numbered migration for later changes. Concurrent startup is protected with a transaction advisory lock.

`createDatabase(pool)` implements the cloud database subset used by the existing handlers: `collection`, immutable `where` / `orderBy` / `skip` / `limit` queries, `get`, `count`, `add`, `update`, `remove`, document `get` / `update` / `remove` / `set`, comparison commands, atomic increments and regular expressions. Unknown collection names fail immediately. Query values and extension keys are parameterized.

## Storage contract

- All 24 collections have their own typed SQL table. Camel-case API fields map explicitly to snake-case columns. Existing cloud document IDs remain opaque text, and new IDs are UUIDs generated by Node.js.
- Events use `timestamptz` and round-trip to epoch milliseconds at the API boundary. Monetary values use `numeric(14,2)`; API numbers remain compatible with current handlers. Points and counters use integers.
- Users, jobs, applications, enrollment, insurance purchases, moderation, uploads and audit records have foreign keys. Empty optional foreign-key strings become SQL `NULL`. Parent users/jobs/products are retained for history; application code normally disables or soft-deletes them.
- Categories must be seeded before jobs. Foreign keys are deferred until transaction commit, allowing a complete import to insert dependent collections in any order. Existing demo counters must be integers.
- Enterprise profile fields are typed one-to-one columns on `users`. Resume skill names and file references are text arrays. Arbitrary operational configuration values and payment-provider payloads are JSONB. `attrs` stores optional extension fields; core fields are never copied there.
- Applicant names/job titles and purchased insurance name/price are historical snapshots, intentionally retained when the source profile or product changes. Wallet `business_id` and audit `target_id` refer to multiple entity types, so they remain polymorphic strings.
- Unique constraints protect users' OpenIDs, administrator names, configuration keys, category keys, active applications, favorites, unlocks, course enrollment and active blacklist reports. Payment order numbers, provider transaction IDs and recharge ledger entries also have deduplication constraints.

## Transactions

Architecture v1 adds `jobs.version`, `job_reviews` and durable `command_receipts` through `002_architecture_v1.sql`. Migrated commands use explicit application transactions with the same shared write lock as legacy handlers. The finance report alone uses a repeatable-read, read-only transaction without that lock. See [the v1 rollout and compatibility notes](../../docs/架构优化第一版.md).

Wrap complete business requests in `db.runInTransaction(async () => ...)`. The callback's return value is passed through; `{ success: false }` rolls back, as does a thrown error. The callback optionally receives a transaction-bound database. A manual `db.startTransaction()` provides `collection`, `commit` and `rollback`; nesting uses savepoints. A swallowed SQL error cannot produce a successful commit response.

The default `{ write: true }` acquires a database-wide transaction advisory lock **before** any business reads. This intentionally serializes existing read/check/update workflows, including profile rewards and payments, until they can be migrated individually to row locks or fully atomic SQL. All current legacy API routes should use this default because some GET handlers update counters or expire jobs. `{ write: false }` is available for genuinely read-only callers; a later mutation acquires the same lock but cannot protect reads performed before that upgrade.

Single mutations outside an explicit transaction open their own locked transaction. Reads outside a transaction use the pool directly. `pool` lifecycle remains the caller's responsibility.

## Verification

Set `TEST_DATABASE_URL` to a disposable PostgreSQL database and run `node --test server/test/db.test.cjs` from the repository root. The suite creates an isolated random schema, runs migrations twice, checks typed mappings and actual CRUD, tests rollback/savepoints and constraints, exercises concurrent read/update and sign-in flows, then replays concurrent payment callbacks to prove a single credit/ledger write. The schema is removed at the end. Without that environment variable the suite is skipped.
